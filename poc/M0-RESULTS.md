# M0 验证结果 · macOS 第 1 轮

> 2026-11-07 · macOS 27.0.1 · Apple Silicon · 60Hz 显示器 · release 构建
> 原始数据：`~/Library/Logs/com.anytools.poc/m0-metrics.jsonl`（共 12 次唤起）

## 结论

| # | 验证项 | 结果 | 说明 |
|---|---|---|---|
| P1 | 钩子与吞键 | ✅ 通过 | 内核事件到钩子回调 0.07–0.32ms；回调耗时 5–26µs（首次冷启动 338µs），远低于系统超时停用的门槛；钩子没有被系统停用过 |
| P1 | 不抢焦点 | ✅ 通过 | 从其他应用唤起 6 次（Claude、终端、Finder），前台应用一次都没变 |

| P1 | 发出的按键被原应用收到 | ⚪ 未测 | 执行过的 2 个动作（打开面板、启动终端）都成功，但都不涉及向其他应用发按键或输入文本 |

| P4 | 流动辉光不掉帧（CSS） | ✅ 通过（60Hz） | 1628 帧中掉 2 帧（0.12%），都出现在唤起或执行的当下 |

## P1 延迟分解

| 阶段 | 耗时 |
|---|---|
| 内核事件 → 钩子回调 | 0.07–0.32ms |
| 钩子 → 原生窗口显示（毛玻璃开始淡入） | 1.1–5.2ms |
| 钩子 → 事件到达 WebView（Tauri emit） | 2.7–17.7ms |
| WebView 收到事件 → 画完 | **43–117ms** |

绝大部分时间花在 WebView 里。注意：「画完」是在连续两次 `requestAnimationFrame` 之后上报的，比真实的第一帧晚约 1 帧（16.7ms）。扣掉这一帧，中位数仍在 50ms 以上。

可能的原因（尚未逐一验证）：
1. **隐藏窗口里的 WebView 被节流。** 默认的「orderOut」方式会把窗口移出屏幕，WebKit 会暂停这个页面的渲染，窗口重新显示后要等它恢复。面板里「显示方式 › alpha」就是用来验证这一点的，这轮没有切换。
2. **每次唤起都重建整个 SVG，并且用 `feTurbulence` 实时生成噪点纹理。** 噪点滤镜渲染很贵，应该改成预先做好的图片；DOM 应该在启动时建好，唤起时只更新内容。
3. Tauri 事件系统的传递延迟有时达到 15ms，可以换成 `Channel` 或直接在 WebView 里执行脚本。

## 这轮没覆盖到的

- 向其他应用发快捷键或输入文本，以及松开后有没有多出来的空格。
- WebGL 辉光、120Hz 屏幕。
- 桌面上选中的文件、一次选中很多文件时的读取耗时（这轮最多选中了 1 个）。
- 多显示器、全屏应用、其他桌面空间。
- Windows 部分的全部验证项。

# 第 2 轮 · 首帧延迟优化（自动测试）

> 2026-11-07 · 同一台机器 · release 构建 · `ANYTOOLS_SELFTEST=12`：程序自己走和钩子相同的代码路径唤起轮盘，再用 Esc 取消，不向系统注入任何键鼠事件，也不会执行任何轮盘动作（`exec` 记录为 0 条）。两种显示方式各测 12 次，每次唤起间隔 2 秒。

## 找到的根因

**窗口不可见时，WebKit 会把页面标为隐藏，停掉渲染和 `requestAnimationFrame`。** 窗口透明度为 0 时也会这样，因为 AppKit 把这种窗口当作被遮挡了。所以唤起时页面要先从「隐藏」恢复，才能画出第一帧。第 1 轮里，网页收到事件到画完要 43–117ms，主要就是这个原因。

## 改动

1. **关掉 WKWebView 的窗口遮挡检测**（`_setWindowOcclusionDetectionEnabled:`，私有接口，运行时先检查是否存在，在这台机器上存在）。窗口透明度为 0 时，页面也保持「可见」，可以正常渲染。
2. **默认轮盘提前画好。** 两次唤起之间，窗口始终放在屏幕上，透明度为 0，里面的默认轮盘已经完整渲染。唤起时由原生代码直接把窗口淡入（110ms），第一帧完全不等网页。网页只负责后续的弹簧放大、中心文字和切换轮盘。
3. **所有轮盘的 DOM 在启动时一次性建好**，唤起时只切换显示哪个轮盘。实时生成噪点的 `feTurbulence` 滤镜换成了启动时生成一次的噪点图片。
4. 辉光动画在不显示时暂停。窗口隐藏期间没有 rAF 循环，也没有 CSS 动画在跑。

## 结果

| 指标 | alpha（新默认） | orderOut（对照） | 第 1 轮 |
|---|---|---|---|
| 唤起时页面状态 | 12/12 可见且已画好 | 12/12 隐藏 | 隐藏 |
| 钩子 → 原生窗口开始淡入 | p50 1.2 / p95 6.2ms | p50 1.9 / p95 3.0ms | 1.1–5.2ms |
| **按键 → 首帧可见（估算）** | **p50 18 / p95 23ms ✅** | p50 19 / p95 20ms，但首帧可能是旧画面 | 中位数 68ms |
| 钩子 → 页面更新画完（上限） | p50 41 / p95 43ms | p50 51 / p95 63ms | 中位数 68ms |
| 页面收到事件 → 第一次 rAF | p50 2ms | p50 25ms | — |
| 掉帧 | 495 帧中 0 帧 | | |
| 抢焦点 | 24 次中 0 次 | | |
| 空闲 CPU（测试结束后，含 WebKit 子进程） | 0.0% | | |

**P1 的 ≤ 50ms 现在通过了**：首帧估算 p95 23ms；即使按页面更新画完的时间算（这个值偏大，连续两次 rAF 本身就多出约 1 帧），p95 也只有 43ms。

「首帧可见」的估算方法：内核到钩子的时间（第 1 轮实测 ≤ 0.3ms）＋ 钩子到原生窗口开始淡入 ＋ 1 个显示帧（WindowServer 合成）。这一项**没有用录屏实际测量**，因为截屏需要「屏幕录制」权限。前提是 WindowServer 会在下一帧就合成这次透明度变化。

## 剩下的风险

- `_setWindowOcclusionDetectionEnabled:` 是私有接口，系统更新后可能被移除。代码在调用前会先检查；接口不存在时，退回到第 1 轮的表现（约 68ms），功能不受影响。正式产品里要做成：检测到接口不存在就报告，并保留降级路径。
- 用 orderOut 方式时，首帧仍然可能是上次留下的旧画面，所以默认改成了 alpha。
- 透明窗口一直留在屏幕上。它已经设置了不响应鼠标、不参与窗口切换，还需要你实际确认：没有挡住点击，在调度中心、全屏应用里也正常。

## 面板的一个统计错误（已修正源码，下次打包生效）

「不抢焦点」一行把「本来就是在 PoC 面板里唤起」的 6 次也算成了抢焦点，所以显示为未通过。这几次前台本来就是我们自己，不应该计入。现在只统计从其他应用唤起的情况。
